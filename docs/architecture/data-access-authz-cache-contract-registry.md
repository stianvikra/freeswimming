# Data Access Authz Cache Contract Registry

## Purpose

This registry is the canonical route-level contract for data access, authz, service-role usage,
and cache behavior across `app/**/route.ts`.

Use it before adding or changing any route handler that touches Supabase, authenticated identity,
admin/editor permissions, entitlements, provider side effects, or user-specific data.

Inventory baseline:

- `69` route handlers under `app/**/route.ts`.
- Auth helpers: `lib/supabase/server.ts`, `lib/supabase/route-handler.ts`,
  `lib/supabase/admin.ts`, and `lib/admin/server.ts`.
- Operational runbooks: `docs/runbooks/supabase-egress-response.md`,
  `docs/runbooks/auth-account-support.md`, `docs/runbooks/gdpr-data-rights.md`,
  `docs/runbooks/qr-redirect-operations.md`, and `docs/runbooks/core-flow-incident-response.md`.
- External service/provider matrix:
  `docs/architecture/external-service-contract-matrix.md`.

## Route Classes

| Class                      | Contract                                                                                                                                      |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `public`                   | No user identity is required. Route must not create a Supabase auth client unless it is intentionally reading public server data.             |
| `public-optional-identity` | Route works without cookies and may attach `user.id` only when an auth token cookie exists. No-cookie paths should use cookie-gated helpers.  |
| `auth-session`             | Route exchanges or clears auth/session state. It may write cookies and must redirect or return deterministic errors without exposing tokens.  |
| `protected-user`           | Route requires an authenticated user. Reads/writes are server-canonical and should be owner-scoped through RLS or explicit `user.id` filters. |
| `entitlement-protected`    | Route requires an authenticated user plus an entitlement, purchase, or billing relationship. Finance-relevant IDs must stay reconcilable.     |
| `admin-viewer`             | Route requires authenticated admin viewer access or higher. It may read private admin state but cannot mutate protected content.              |
| `admin-editor`             | Route requires editor access for mutation; destructive, import, restore, or system-level actions may require `admin`.                         |
| `service-role`             | Route uses `createAdminSupabaseClient()`. Use only after an admin gate or inside trusted server-only/provider flows such as Stripe webhooks.  |
| `dev-only`                 | Route is local/dev-support only and must stay disabled or fail closed outside approved development mode.                                      |

## Helper Contract

| Helper                                                  | Allowed use                                                                                                                                      | Required evidence                                                                                                                 |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| `createRouteHandlerSupabaseClient()`                    | Protected route handlers that need cookie writes via `applySupabaseCookies()`.                                                                   | Route must call `supabase.auth.getUser()` directly or through `requireAdminRoleFromSupabase()` before protected data access.      |
| `createRouteHandlerSupabaseClientIfAuthCookiePresent()` | Public optional-identity routes where no-cookie traffic must not call Supabase Auth.                                                             | Unit test or route review showing fallback response without creating a Supabase client.                                           |
| `getServerSupabaseUserIfAuthCookiePresent()`            | Server components or route handlers that can operate anonymously but should attach identity when present.                                        | No-cookie path must return anonymous/fallback behavior without `auth.getUser()` traffic.                                          |
| `createServerSupabaseClient()`                          | Auth callback/session routes, protected user routes that cannot use route-handler cookie application, or intentional public server data lookups. | Route registry entry must justify why cookie-gated helper is not used.                                                            |
| `createAdminSupabaseClient()`                           | Trusted service-role work: admin-gated repair/storage cleanup, Stripe/webhook fulfillment, catalog sync, entitlement repair, or GDPR deletion.   | Route must be admin-gated first, or the route must be a trusted provider/server-only entrypoint with signature/intent validation. |
| `requireAdminRoleFromSupabase()`                        | Admin route guard.                                                                                                                               | Entry must name minimum role: `viewer`, `editor`, or `admin`.                                                                     |

## Cache Contract

Default expectations:

- Protected JSON and mutation routes return `Cache-Control: no-store`.
- User-owned exports return `Cache-Control: no-store` or `private, no-store`.
- Public optional-identity routes use `force-dynamic` when they inspect cookies, runtime flags, or request-specific state.
- Provider webhooks and POST side-effect routes are not publicly cacheable; if they do not emit a cache header today, do not add caching in feature work.
- Redirect routes that expose private preview, QR, auth, or dev state use `no-store` when route-local headers are present.

New or changed routes must explicitly choose one:

- `no-store` for private/protected/user-specific data,
- `private, no-store` for user-specific downloadable artifacts,
- `public static/cacheable` with no Supabase identity access,
- `dynamic fallback` with cookie-gated optional identity,
- or a documented route-specific invalidation trigger.

## Change Gate

Before changing or adding a route handler:

1. Add or update the route row in this registry.
2. Name the route class, canonical data, auth helper, service-role status, cache mode, and expected failure statuses.
3. Add the cheapest matching test layer:
   - unit route test for parser/helper/branch behavior,
   - E2E security test for representative protected/admin HTTP behavior,
   - runbook evidence when the route is operational/provider-facing.
4. If the change renames a route, label, workflow action, support path, Help/Guide assertion, or recovery behavior, run the route-label/support sweep.
5. For any route that introduces service-role access, document why user-scoped RLS is insufficient and where the gate/signature/idempotency proof lives.
6. For any route that introduces or changes a provider side effect, update the external service matrix for service key, docs baseline, secret boundary, retry/idempotency, diagnostics, and rollback.

## Deferred Runtime Enforcement

This registry found no immediate P0 security, data-integrity, or cache blocker requiring runtime changes in the registry PR. Runtime enforcement should be split into a child brief if a future route sweep finds:

- a public/no-cookie route creating unnecessary Supabase auth traffic,
- a service-role call before an admin or provider trust gate,
- a protected artifact response missing private/no-store semantics,
- an admin/user route returning non-deterministic or sensitive errors,
- or a route without a maintainable negative-path test strategy.
