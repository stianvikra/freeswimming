# Auth And Account Support

Use this runbook when users ask where account, sign-in, billing, or recovery actions live.

## Current Product Contract

- `My Library` is the account home.
- The signed-in email is shown on `My Library`.
- `Manage billing` lives on `My Library` and opens the Stripe Billing Portal for the authenticated user's Stripe customer.
- `Sign out` lives on `My Library`.
- `/auth/sign-in` owns secure email-link sign-in plus one-time-code fallback, resend, cooldown, and spam/junk-folder guidance.
- `/auth/sign-in` uses safe `next` and `source` query context for explanation copy only. It does not grant admin, billing, entitlement, or download access.
- `/preview-access` owns private preview unlock guidance when site-lock is enabled.
- `/my-library/security` is a legacy protected route that redirects signed-in users to `My Library`.

## My Library IA

- Signed-in Home has two direct routine actions under `Free course`: `Micro Sessions` for the active weekly micro plan or creation state, and `Habits` for today's check-ins or add-habit state. Mobile Home entries prioritize execution: active micro plans open in compact `Bubbles` mode and Habits opens the active habit rows before weekly stats.
- `My Routines` sits under `Free Course` on `My Library` as one simple `Open` row. It opens `/my-library/routines`, where users switch between `Micro Sessions` and `Habits`. `Micro Sessions` `Open` jumps to the full active/setup Micro Sessions surface; `Edit` opens micro-plan editing.
- Mobile navigation uses the topbar hamburger as the global menu everywhere. The floating mobile nav is contextual: public pages use `Home / Course / Programs`, routine pages use `Library / Micro / Habits`, and other My Library pages use `Library / Routines / <current section>`. `Home` is not relabelled as `Back`; local back links keep deterministic parent fallbacks.
- `My Swim Profile` holds swimmer identity, CSS, preferences, personal records, and optional advanced generator limits. First-use opens one recommended setup action; other sections remain reachable from the readiness summary and section toggles.
- `Goals` (`/my-library/goals`) is the compact long-term target surface. Users work from the current goal list, use the single `Active`/`Achieved`/`Archived`/`All` filter, open `Add goal` for template/custom creation, and open a goal's `Details` for `Use as focus`, `Add note`, `Archive`, `Restore`, or `Clear best result`. `Request coaching schedule` is one footer CTA to `/contact?source=goals_coaching`.
- `My Training` (`/my-library/training`) is retained for contextual goals-to-focus links and notes, but it is not a top-level My Library card while focus/observations are being moved closer to session and history workflows.
- `Habits` (`/my-library/habits`) holds the private `My Perfect Day` habit setup, daily check-ins, reset behavior, and small weekly consistency summary. It is reached from signed-in Home or `/my-library/routines`, not a duplicate top-level My Library card.
- `Calendar` (`/my-library/calendar`) is the private My Library calendar surface with `Plan` and `Stats` tabs. `Plan` reads owner-scoped `planned_workout_instances` created from saved program assignments and shows planned swim sessions only; desktop uses a wider app workspace with a Garmin-style month table where each visible week has a `Week total` column after Sunday, and selected-day details sit below the month. Mobile keeps the selected Monday-Sunday week/day cards. Today is a single blue date dot, dates before today use muted date numbers, selected day is a blue cell boundary, and `Previous`/`Today`/`Next` navigation stays visible. Month cells are scan-only day selectors. Selected-day detail owns plan-item actions: `Reschedule` sets a manual planned-date override, `Skip` and `Cancel` are reversible planned-only statuses, and `Recover` returns skipped/cancelled rows to `planned`. These are not completion history, and they do not mark a workout done. Program/workout source edits still live in their editors. Drag/drop, Garmin sync, and actual completed activity events are not connected yet. Unknown future planned-instance statuses show `Review status` and should not be treated as completed history. `Stats` is backed by the existing `view=compare` route: it shows source/period controls before the strongest period trend, key takeaways, source signals, and secondary detailed numbers for supported `source`/`period` URL params. Habit percent comparisons show direct values such as `30% vs 66%` instead of percentage-point wording, and period text should say `last week`, `last month`, or `last year` unless the user selected an explicit comparison date. `Habits`, `Micro Sessions`, and `Dryland` are counted from existing owner-scoped data; the Habits source also shows active habit count, included habit names, tracked days, and separate habit stat reset markers so the comparison is explainable. Reset markers restart motivation stats only and are not counted as completed habits, rest days, or slips. `Micro Sessions` means saved micro-plan blocks here. `Dryland` currently compares completed saved sessions and training minutes only; strength sets/reps/load and stretching hold time require a future mapping. `Swimming` is shown as not included yet until saved swim sessions have a canonical completed-on date.
- `My Swim Sessions` (`/my-library/workouts`) is the saved swim-session list and swim builder entrypoint.
- `Dryland Sessions` (`/my-library/dryland`) is the saved strength/stretching list, dryland builder entrypoint, and compact weekly `Micro Sessions` execution surface. The default route shows create actions and saved sessions before the weekly Micro Session panel; micro-focused query links prioritize the Micro Session surface. Saved sessions show normal `Edit`/`Open`/`Delete` actions by default; Micro Session source checkboxes appear only inside explicit create/edit mode.
- `Program builder` is optional and only for placing saved swim sessions into week/day slots.

## Support Answers

- If a user asks which email is signed in: send them to `My Library`.
- If a user wants to sign out: use `Sign out` on `My Library`.
- If a user needs billing or invoices: use `Manage billing` on `My Library`.
- If the Stripe Billing Portal says there is no invoice history after a one-time Checkout purchase:
  - verify the authenticated app user owns an entitlement row with the same `stripe_customer_id` as the Stripe customer opened in the portal,
  - do not open a Stripe customer found by email unless the app user already owns an entitlement that needs its missing `stripe_customer_id` repaired,
  - verify the Checkout Session has `payment_status=paid`,
  - verify `invoice_creation.enabled=true` and an invoice ID exists for the session,
  - treat older sandbox purchases made before invoice creation was enabled as receipt/charge-only records; they do not retroactively gain portal invoice history.
- If a Checkout Session, webhook analytics row, or entitlement row has workout-context attribution
  such as `source=workout_context` and `placementId=workout_saved_post_success`, treat it as safe
  product telemetry/support context only. It can help diagnose the saved-workout-to-plans path, but
  it is not revenue, refund, payout, invoice, accounting, Stripe reconciliation, unique-user
  conversion, or app access proof by itself.
- If a sign-in email does not arrive: ask them to check spam/junk, wait for any cooldown, then request a new sign-in email on `/auth/sign-in`.
- If the secure email link does not open: ask them to enter the one-time code from the same email on `/auth/sign-in`.
- If an iPhone Home Screen app user says the email link opens in Safari or Safari denies the sign-in:
  ask them to return to the Home Screen app and enter the one-time code from the same email.
- If `/auth/sign-in?next=/admin` is shown: explain that sign-in confirms identity only. Admin access is checked after sign-in by the app's admin authorization layer.
- If the Admin Users tab count disagrees with Supabase Auth: treat Supabase Auth users as the canonical account list. `profiles`, `athlete_profiles`, entitlements, and activity are enrichment only. Diagnose with the Auth user ID, email confirmation state, profile status, role source, entitlement count, latest safe product activity timestamp, and bounded support codes; do not ask for raw private training, habit, workout, note, analytics payload, IP, User-Agent, provider, invoice, refund, or payout data.
- If Admin Users shows `missing_profile`: the Auth account exists but the public profile mirror is absent. The account must still remain visible. Use the role-change repair path only when an admin is intentionally setting the user's role and the Auth user has an email; otherwise record the support code and repair the profile mirror through the approved admin/data path.
- If Admin Users shows `profile_email_mismatch`: do not hide or merge the account by email. Use the Auth user ID as identity, confirm which profile row is stale, and repair the mirror through an approved admin/data path before treating email as support truth.
- If a role must change: only an effective `admin` may use the Users role control. Require a typed reason, confirmation, expected-current-role check, and audit log. Viewer/editor admins may inspect the permitted summary but cannot change roles. Last-admin demotion must stay blocked.
- If someone asks whether a `viewer` is a test user: answer no. Admin `viewer` is an admin-console permission level. Tester/test-viewer status is a separate access lifecycle signal and should not be inferred from admin role.
- If the user lands on sign-in from My Library: they should verify with the email they use for the app, then return to My Library or the member page they opened.
- If the user lands on sign-in from checkout success or claim/download recovery: ask them to use the same email they used at checkout. Do not promise that a purchase, invoice, billing portal access, entitlement, or download exists until the normal checks complete.
- If a checkout/claim link fails and returns to sign-in: the visible context copy may persist through a safe `source` value, but support should still diagnose entitlement, billing, and download ownership separately.
- If a user is on `/checkout/success` or `/claim`: the supported recovery path is `Continue to My Library` or `Sign in to My Library` first, then the access-link resend form with the checkout email if they still cannot open owned items. The resend response is intentionally generic and does not confirm whether that email has a purchase.
- If the email only contains a code and no button/link: check the Supabase Magic Link email template
  includes both `{{ .ConfirmationURL }}` and `{{ .Token }}` plus the hosted PNG brand lockup.
- If `/auth/sign-in` shows "Sign-in is temporarily unavailable because a service limit was reached":
  - check Vercel logs for `[Auth] Could not request sign-in email` with `kind: "service_restricted"`,
  - confirm the admin incident alert `auth_sign_in_service_restricted` was sent or intentionally disabled by `INCIDENT_ALERTS_ENABLED=0`,
  - check Supabase Dashboard -> Organization Usage -> Egress for `exceed_egress_quota` or Fair Use restrictions,
  - do not ask the user to retry repeatedly until Supabase usage/billing restriction is resolved,
  - tell the user sign-in is temporarily unavailable and that we are resolving a service limit.
- If `/auth/sign-in` shows "Email code could not be sent right now":
  - check Vercel logs for `[Auth] Could not request sign-in email` with `kind: "email_delivery"`,
  - confirm the admin incident alert `auth_sign_in_email_delivery_failed` was sent or intentionally disabled,
  - inspect `MESSAGE_DELIVERY_*`/Supabase email provider state before asking the user to retry.
- If a one-time code expires or fails: request a new sign-in email from `/auth/sign-in`.
- If preview access is blocked while the site is private: authenticated admins should be issued access automatically through `/preview-access/admin-unlock`; anonymous visitors and non-admin testers still use `/preview-access` until the test-user access brief ships. A `preview_access_unlock_failed` incident alert means an authenticated admin passed the admin gate, but strong session claims could not be verified.
- If the `My Routines` route looks stale: diagnose the underlying `Habits` and `Dryland Sessions` data separately. `My Routines` has local-only tab state and no reminder table, push subscription, background job, or persisted pinning state in V1.
- If a user cannot find `Use as focus`, `Add note`, `Archive`, `Restore`, or `Clear best result` on `Goals`: ask them to open the goal row's `Details`. The visible row keeps one primary action; management and My Training bridge actions are intentionally tucked behind `Details`.
- If a user says `My Swim Profile` is hiding profile setup: ask them to use the `Profile readiness` summary at the top, then open the recommended action or the relevant section toggle. Unsaved local drafts keep their section open and show restored-draft copy; saved state is still the owner-scoped server data.
- If advanced generator limits fail to save on `My Swim Profile`: verify the linked Supabase environment has applied `20260502120000_swim_capability_limits.sql` and `20260516120000_replace_swim_capability_limits_rpc.sql`, then confirm the authenticated owner can execute `replace_swim_capability_limits(jsonb)`. Do not ask the user for raw profile values or capability details; diagnose with schema/RLS/RPC state, redacted timestamps, and whether previous limits remain intact after the failed save.
- If `Micro Sessions` shows "still syncing" under `Dryland Sessions`: verify the linked Supabase environment has applied `20260508101500_dryland_micro_plans.sql`, then confirm `dryland_micro_plans` RLS allows owner-scoped authenticated reads/writes. Saved dryland sessions should remain available while this is repaired.
- If an iPhone Home Screen user sees `No internet`: ask them to reconnect and tap `Retry`. The installed app has an offline fallback page because standalone iOS web apps do not expose Safari's normal refresh button.
- If a user cannot find the normal `Edit`/`Open`/`Delete` saved-session actions under `Dryland Sessions`: check whether Micro Session create/edit source-selection mode is open. In that mode, the same saved sessions are shown as compact source checkboxes with direct `Edit` links; update or cancel the Micro Session edit to return to the normal saved-session list.
- If `/my-library/calendar` looks wrong: first check `view`. For `Plan`, verify `programs.starts_on`, `planned_workout_instances`, the selected `date`, and whether the device is using desktop month view with the `Week total` column or mobile week/day cards; the same owner-scoped planned instances should drive both. `Today` always points to the normalized current day and uses the blue date dot; dates before today use muted date numbers; the selected day uses selected cell styling without implying completion. Each `Week total` cell is derived from that visible Monday-Sunday calendar row, not from completed history or only the selected week. Missing start week, missing workout, stale update conflicts, and `Review status` are planning repair/review states, not completion history. `Skipped` and `Cancelled` are reversible planned-instance statuses; `Rescheduled` means `date_override_kind = manual` and program sync should preserve that rescheduled date while still allowing source assignment order to update until a separate reorder action exists. For `Stats` (`view=compare`), check the URL `source`, `period`, `date`, and `compareTo` params. Unknown compare values fail closed to an unmapped/not-included-yet state. For missing Swimming numbers, verify whether saved swim sessions have a canonical completed-on date before treating it as a data bug. For missing Dryland strength/stretching details, verify whether the requested field is only available inside saved-session authoring; the compare route does not count sets, reps, weight/load, or stretching hold time until those fields have an explicit comparison mapping.
- If a user asks where the old dryland `Focus cue` went: dryland authoring no longer exposes or writes it. Historical values are preserved only as read-only legacy data and appear in authenticated account exports as `drylandSessions[].legacyFocusText` when present.
- If a Micro Session is stale, complete, wrong, empty, or no longer relevant: use `Clear micro session`. This clears the active weekly surface only; it does not delete saved Dryland Sessions.
- If a user asks why there is no default `Skip set` action: unfinished units now stay open. The supported cleanup path is `Clear micro session` at plan level when the plan should no longer be active.
- If a user edits a saved Dryland Session that feeds the current Micro Session: explain that `Save` applies to future Micro Sessions by default. Use `Update current micro session` only after saving when they deliberately want remaining queued units rebuilt; completed/skipped units are preserved.
- If a user reports that `Available units` or `Done` disappeared while editing a Micro Session: confirm they are in edit mode. Edit mode is configuration-only; training execution actions return after `Update micro session`, `Cancel`, or `Close edit`.
- If a user asks what happened to `Manual release`: it is no longer offered when creating or editing a Micro Session. Existing legacy manual-release units remain readable and can still use `Release now`; ask the user to choose `Available now` or `Weekday release` before saving edits to a legacy manual plan.
- If a user reports that a Micro Sessions bubble did not pop, complete, or play sound: first confirm whether they are in `Ordered` or `Bubbles` mode under `Dryland Sessions`. In `Bubbles`, reps-based units still use the two-step `Complete?` path: first tap/click or `Enter` arms the bubble, the second confirms completion, and `Escape` cancels. Duration-based bubbles first open in place with `Start`; after start, the bubble shows a local countdown and auto-completes through the same owner-scoped micro-plan `PATCH` path when it reaches zero. If the user taps a running timed bubble before zero, the UI asks for `Complete?`; if they do not confirm within about one second, the countdown resumes. Completed bubbles leave the open board, and the stable `Undo` button restores completed units in reverse order. Bubble mode exposes direct `Edit`, `Clear`, and icon-only sound controls on one row instead of a `Manage micro session` accordion; normal active plans do not offer a visible `Pause` action, while already-paused plans still show `Resume`. Micro Sessions sound is a separate local-only, default-off, icon-only preference: enabling it previews the tap profile, server-confirmed reps/tap completions use the tap profile, duration/timer completions use the timer profile, and failed saves, undo/restore, page load, hydration, skipped/unfinished units, and clearing the plan do not play sound. If the bubble remains visible with an error, diagnose the existing micro-plan `PATCH` path and do not look for stored timer/drag/pop/audio/haptic telemetry because bubble presentation, countdown, and audio state are not persisted.
- If `Habits` shows "still syncing": verify the linked Supabase environment has applied `20260510153000_habits_perfect_day_foundation.sql`, `20260512103000_habits_v2_build_quit_timed_tracking.sql`, `20260513213000_habits_cadence_priority_contract.sql`, and `20260607143000_habits_stats_reset_events.sql`, then confirm `habit_definitions`, `habit_check_ins`, and `habit_motivation_resets` RLS allow only owner-scoped authenticated reads/writes.
- Habits now support user-facing `Do`, `Quit`, and `Timed` modes plus explicit cadence fields: `cadence_period`, `cadence_target_count`, `cadence_day_policy`, and legacy-compatible `schedule_days`. `Do` is stored internally as `habit_mode = build` for compatibility. `Add habit` opens a focused create surface in view on mobile and near the top of the Habits surface on desktop; after `Create habit`, the new row receives focus and shows `Habit added` inside the card. `/my-library/habits?date=YYYY-MM-DD` selects a Habits history day, week controls move through ISO Monday-Sunday weeks, Today returns to the current day, selected-day/week links do not use `#today-habits` so day changes should keep the Weekly Overview in context, the selected week shows ISO week number/year plus date range, upcoming days in the current week are disabled, and invalid/future route dates load Today. The Habits heading area shows a truthful status line such as `Today: 6/7 · Week: 1/2 · Month: 1/3 · May 10`, with `Week` and `Month` shown only when active habits exist for those cadence periods; Today appends the date only, while historical selected-date context uses `This day` plus weekday/date such as `This day: 0/1 · Sat · Jun 6`. Requested dates show pending feedback while loading; if the requested date fails, the UI falls back to the last confirmed date and must not be treated as loaded for the failed date. Past selected dates allow correcting eligible existing habit check-ins for that date; `Add habit`, row `Edit this habit`, `End habit and move to Past habits`, and `Restore habit` stay Today-only so support should diagnose setup changes separately from historical check-in correction. `Do` target setup separates `Done only` / `Any amount` reminders from specific count, duration, time-of-day, and avoid/limit targets. Permanent hard delete is not shipped in this flow. Open `Details` shows one cadence/start-date metadata line with the year, for example `Daily · Started Jun 7, 2026`, and does not repeat setup/status/category pills such as `Do`, `Open`, `Other`, or `Done only`. Per-habit `Completion saved.` feedback appears inside the habit card that saved and clears after about 3 seconds. `Undo complete` removes a completed binary check-in; for timed completions it removes only the latest timer source and preserves manual minutes when present, while `Undo rest day` and `Undo slip` name those separate states. `Completion sound` is a local-only Habits preference, defaults off, stores only an enabled flag in browser storage, uses one compact icon-only toggle, previews a short positive ding-style sound when enabled, does not show visible `Sound on.` / `Sound off.` helper text for normal toggles, and should be diagnosed with browser/device mute state, blocked audio, and localStorage availability before treating it as an account or server issue. Sound may play only after mapped successful completion transitions or a same-day timed target signal; it must not play for rest day, slip, reset, archive, undo/restore, failed saves, page load, or hydration. `Rest day` is available from `Details` for non-quit habits and persists as `habit_check_ins.status = skipped`; it is not counted as done or missed for that habit's target. `Quit` habits show days since the selected quit date until a slip exists; when editable and no slip/rest row exists, `Log slip` is a card-level action for the exact selected date. After a slip, Quit habits show consistency such as `9/10 days clear` plus current streak without duplicating a second "days without" counter. `Timed` habits show one daily total from separate `habit_check_ins.timer_seconds`, `manual_minutes`, legacy `value_numeric` where source fields are absent, and any running/paused local timer for Today; timer progress lives in the timer box as compact copy such as `2:05 / 8:00 today`, timer buttons stay action-only, and timer/manual source chips are no longer shown as everyday `Details` copy, so support should diagnose source truth from the row fields instead. `Manual time` is an absolute whole-minute value per habit/date, so saving `5` replaces the manual source instead of adding to a prior `2`; `0` is valid and means no manual time. `Finish` appears on the card once local timer time exists and saves timer seconds while preserving manual minutes; at target, the same-day running timer auto-pauses locally and may play the enabled sound, but it does not save or mark the habit complete until the user chooses `Finish`. Starting another timed habit pauses the current timer locally, and historical timed corrections use `Manual time` rather than starting a past local timer. Habit row cadence chips such as `Daily`, `Weekly - any day`, or `Weekly - 2 fixed days` describe the target schedule; `Done this week/month` means the cadence target is already met for the period, while `7-day minutes` and `7-day count` are report rollups, not weekly goals. Motivation defaults to `Month`/this month to date and can be locally viewed as fixed fresh-start `Week`, `Month`, `Quarter`, `Half-year`, `Year`, or `All`; this only changes derived presentation and does not write habit rows; fixed ranges start at the current calendar boundary and calculate only through the selected date so future days do not count as misses or slips. Current perfect-day streak, best perfect-day streak, perfect days, consistency, rest days, and slips are visible without a `Stats` or `More history` disclosure; zero-value streaks show `0 days`; top-level `Timed minutes` and `Count total` are not Motivation summary cards. `What counts?` defines Perfect days, Perfect-day streak, Best perfect-day streak, Consistency, `0/0`, Rest days, Slips, and Reset habit stats. `Reset habit stats` lives inside a habit's `Details`, creates an owner-scoped row in `habit_motivation_resets`, restarts derived motivation stats from the selected date, shows `Last stats restart <date>` in Details, and links complete history to Calendar Comparison. `/my-library/calendar?view=compare` handles shared week/month/year `Comparison Report` views with `Habits`, `Micro Sessions`, `Dryland`, `Swimming`, and `All` filters: Habits counts existing check-ins/rest/slips/timed minutes and reports reset markers separately, Micro Sessions counts completed/skipped micro blocks, Dryland counts completed saved sessions and training minutes only, and Swimming is intentionally not mapped until saved swim sessions have a canonical completed-on date. Mobile active Habits links to Habits analysis with `/my-library/calendar?view=compare&source=habits&period=week&date=<selectedDate>`. - Micro-backed Habits are the exception to manual binary completion: if a Habit is linked from Micro Sessions, Habits shows Micro Sessions progress and `Go to Micro Sessions` instead of `Mark done`; completion is written by the linked weekly Micro Session when every unit is done.
- Habits rows now expose tracking-mode labels so support can explain behavior without guessing from counters: `Manual` means the user must explicitly use `Mark done` or `Save`; `Manual timed` means timer/manual time still needs `Finish` or `Save manual time`; `Quit` means clear days are derived until the user explicitly uses `Log slip`; `Source-backed` means a trusted source such as Micro Sessions writes the completion and Habits hides manual `Mark done`. If a user returns after several days away, the Habits absence review can appear only when there is existing tracking history and at least two eligible past habit dates. The review is date-first: Today shows compact past-date rows with `Edit`, Today itself is not listed, the selected historical date uses the normal habit controls, and the bottom review panel repeats the same compact list with `Done with this day` or `Close review` on the last unchecked date. `Done with this day` moves to the next unchecked date; `Close review` returns to Today. Both actions write only local review acknowledgement state; they do not create `habit_check_ins`, mark `Rest day`, log slips, or create `habit_motivation_resets`. `Reset habit stats` remains inside each habit's `Details`; confirming it creates one owner-scoped `habit_motivation_resets` row for that habit and does not delete prior check-ins, so earlier history remains diagnosable through Calendar Comparison.
- Habits `Habit stats` is read-only and derives from existing owner-scoped `habit_definitions`, `habit_check_ins`, and `habit_motivation_resets`. Diagnose mismatched current perfect-day streak, best perfect-day streak, perfect-day count, consistency, rest days, slips, reset boundaries, per-habit `Details` Habit stats, and `Past habits` rows with redacted `habit_id`, `check_in_date`, `status`, `timer_seconds`, `manual_minutes`, `value_numeric`, `value_boolean`, `effective_date`, and `updated_at` fields. Top-level Motivation stats stay visible without a `Stats` disclosure; per-habit `Details` owns each habit's own current/best streak, days completed, consistency, and `Reset habit stats`; timed source diagnostics belong to the check-in row fields rather than visible everyday copy. Unknown or future `habit_definitions.status`, `habit_check_ins.status`, or `habit_motivation_resets.reset_type/status` values must be treated as unsupported and not counted as active, done, rest, slip, reset, or streak-preserving until a typed mapping, tests, and support docs exist. Past habit rows are saved history that can be restored on Today with the same habit ID; do not promise edit-in-history or permanent delete behavior unless a later brief explicitly adds it.
- If Motivation shows `0/0` or `0%`: do not treat it as missing history or a broken chart by itself. `0/0` means there were no scheduled Perfect Day habits in the selected period. `What counts?` is the explanation disclosure; `Past habits` is already visible below it, so do not direct users to `More history`.
- If habit ordering looks wrong: unfinished active rows are intentionally grouped by nearest deadline: due today/daily `Do`, due today `Timed`, `This week`, `This month`, then lower-interruption `Quit status`, completion groups, and later/not-due rows. Stable `sort_order` is the tie-breaker inside the same deadline group. Weekly cadence labels use a calendar week; rolling 7-day summary cards stay labelled `7-day`.
- If cadence diagnostics show impossible values: reject or repair rows where monthly fixed dates are present, weekly targets are outside `1..7`, monthly targets are outside `1..31`, daily rows are not `1` fixed daily target, or fixed-day rows have empty/invalid `schedule_days`. Do not expose raw private habit names in support notes.
- If a habit check-in is wrong for today: use `Reset`, `Undo`, or `Undo rest day` on the habit row, then log the correct count, minutes, time, done state, or rest day again. Duplicate same-day build/timed/rest check-ins should update the same `user_id` + `habit_id` + `check_in_date` row, not create multiple competing facts.
- If a quit habit shows the wrong days-since or consistency count: verify `habit_definitions.start_date`, `habit_definitions.last_lapse_date`, and owner-scoped `habit_check_ins.value_boolean = false` lapse rows from the quit date through the selected date. Use `Undo slip` if today was logged by mistake; do not ask the user to describe the sensitive habit label.
- If a timed habit timer fails or the browser closes before saving: same-day running/paused timer state is persisted locally per user, habit, and date, but remains local-only until `Finish` writes `timer_seconds` or `Manual time` writes `manual_minutes` on the owner-scoped check-in row. If local storage is unavailable, corrupted, stale, or from a previous date, the UI falls back to saved timer/manual sources plus legacy `value_numeric` rows. Diagnose server truth by checking `habit_check_ins` for the owner, habit ID, and selected date: `timer_seconds` is saved timer time, `manual_minutes` is the absolute manual source, and `value_numeric` is the compatibility total minutes. The visible total may include unsaved local timer state, so do not treat local timer state alone as completion evidence.
- If a user asks whether habit labels such as weight-loss, sugar, chips, smoking, wake time, or reading habits are used for public analytics: treat habit names, quit goals, lapses, notes, and check-ins as private training/life data. Do not ask the user to send sensitive habit details; diagnose with row existence, timestamps, status, mode, schema/RLS state, and redacted analytics payloads instead.

## Security Rules

- Do not ask users to send sign-in links, one-time codes, session cookies, or raw auth errors.
- Do not expose another user's email, Stripe customer, invoice, or entitlement data while diagnosing support cases.
- Account email is display identity, not a route identifier or authorization key by itself.
- Passkeys and Face ID are not live account-management features until a separate auth architecture brief ships them.
